What changes across models

Qwen, Kimi, and MiniMax reach the top tier.

Their Gigatoken hot paths stabilize around 76–85 Mtok/s at long lengths.

GLM settles near 58–65 Mtok/s.

Its 3-digit pretokenizer costs more, but scaling stays linear and predictable.

DeepSeek-V4 is the hardest scheme.

It plateaus near 42–45 Mtok/s, still 7–11× faster than valid Fastokens cells.

Prototype integration

JSON path

tokenizer.json → Gigatoken BPE encoder → Dynamo Encoding
token IDs → Hugging Face decoder

Kimi path

tiktoken.model + tokenizer_config → Gigatoken Kimi encoder
token IDs → Dynamo TikToken decoder

  • Gigatoken matched official reference IDs for all 175 timed text inputs: five models × five lengths × seven rotations.
  • The adapter now supports both Hugging Face byte-level BPE JSON and native rank-per-line TikToken models with an explicit pretokenizer scheme.
  • Decode remains on the established Dynamo backend; these results measure encode only.
  • Config-only special tokens are not imported into Gigatoken yet; timed inputs avoid that unresolved parity surface.
  • Prefix-cache wrapping is still conservatively rejected pending boundary qualification.

Findings

Gigatoken’s advantage is robust, not Qwen-specific.

Every model and length is materially faster than its official reference.

Model choice changes absolute throughput by ~2×.

At 32K, DeepSeek runs at 44.7 Mtok/s versus MiniMax at 83.4.

Fastokens is much closer to Gigatoken than HF, when it works.

The valid-cell gap is 7.3–13.9×, compared with 38.6–199.2× over references.

Kimi is the strongest relative result.

Native Gigatoken rank-file encoding is roughly 48–73× faster than Dynamo TikToken.

Gaps and limitations

  • Hot cache only: parity checks warm pretoken/BPE caches before timing.
  • Single ASCII-heavy source corpus; multilingual checks are probes, not a performance matrix.
  • One logical CPU, powersave governor, shared host; no architecture or NUMA sweep.
  • Fixed backend order is reference → Fastokens → Gigatoken inside each process.
  • No batch-size, concurrency, prefix-cache, cold-unique, or end-to-end frontend measurements.
  • No per-backend RSS isolation; construction time does not include first encode.
  • Gigatoken still requires nightly portable_simd, unstable Cargo profile-rustflags, and a large Python/data dependency closure.
  • The git dependency is not crates.io-packageable as currently specified.

Methodology

  • Intel Core i7-7800X; process and all worker threads pinned to logical CPU 5; RAYON_NUM_THREADS=1.
  • Criterion 0.8.2: 3 s warmup, 7 s target measurement, 60 samples, 95% bootstrap CI.
  • Fresh process per model/length; release binary built once before timing.
  • Seven rotating inputs from ten checked-in frontend-crates source files, ASCII-filtered.
  • Inputs are produced by reference encode → exact token prefix → decode → exact re-encode.
  • Every present candidate backend must return the same IDs for all seven inputs before timing.
  • Reported throughput derives from exact target tokens divided by Criterion median nanoseconds.

Reproduce

Build once, then run the resulting Criterion binary in a fresh process for each model/length combination:

CARGO_UNSTABLE_PROFILE_RUSTFLAGS=true cargo +nightly build --release -p dynamo-tokenizers --features gigatoken --bench gigatoken_models

taskset -c 5 env RAYON_NUM_THREADS=1 TOKENIZER_BENCH_MODEL=<model> TOKENIZER_BENCH_TARGET=<tokens> TOKENIZER_PATH=<artifact> <bench-binary> --bench --noplot --save-baseline cross-model-20260723

python3 tokenizers/benches/render_gigatoken_report.py

Recommendation

Do not merge the upstream crate directly. The cross-model result is strong enough to justify an upstreamable tokenization-only core: stable Rust, optional Python/data features, explicit HF/TikToken loaders, and a packageable release. Then qualify cold unique prompts, mixed-language/chat/tool corpora, batch/concurrency scaling, memory, prefix-cache boundaries, and full Dynamo frontend CPU/request behavior. Fix the Fastokens PCRE2 chunk-count bug independently before using its long-input results.
